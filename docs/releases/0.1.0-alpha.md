# workctx 0.1.0-alpha

Release date: 2026-08-03

The first alpha of Work Context OS: a local-first, model-neutral work memory and operations system. This release completes the Phase 1 scope — the CLI and durable core — and is intended for early adopters who work file-first and are comfortable with a command-line tool.

## Features

### Contexts and canonical storage

- Isolated context workspaces created from a versioned template (`workctx context init`), each with its own directory tree, projection database, and audit ledger.
- Canonical Markdown/YAML storage with one writer per context: locking with stale-lock recovery and fencing, staged atomic multi-file writes, and write-ahead intent records for crash recovery (ADR 0006).
- Workspace validation with stable diagnostic codes and repair guidance (`workctx context validate`, alias `workctx validate`).

### Evidence lifecycle

- Inbox registration with streaming SHA-256 hashing, typed manifests, and idempotent re-registration (`workctx inbox add`).
- Safety scanning at the door: artifacts containing possible secrets or instruction-like content are quarantined, and quarantined bytes never reach proposals, reports, views, or diagnostics.
- Post-commit archive: originals move to `01_processed/` only after the transaction that consumed them commits.

### Transactions and audit

- Typed multi-entity transaction proposals, validated and previewable without side effects (`workctx proposal validate`, `workctx transaction apply --dry-run`).
- Atomic, explicitly approved apply under the context lock (`workctx transaction apply --yes`).
- Append-only, hash-chained audit ledger with verification, summaries, and per-event lookup (`workctx transaction history`, `workctx transaction show`; ADR 0010).

### Retrieval and views

- Rebuildable SQLite/FTS projections with typed queries and full-text search (`workctx index rebuild`, `workctx search`).
- Reference resolution, typed-relation traversal, and evidence tracing to exact source locators (`workctx ref show|related|trace`).
- Deterministic, budgeted context packs for handing traceable context to a model (`workctx context-pack`).
- Generated operational views — current focus, next actions, waiting on, stale knowledge, and daily brief (`workctx view rebuild`, `workctx brief`).
- Task queries over the projection (`workctx task list|show`).

### Drafting

- Local outbox drafting: agents persist reply and status drafts as canonical documents under `05_outbox/` through an approval-gated tool. The drafting layer has no send, publish, or network primitive of any kind.

### Agent integration

- A stdio MCP server bound to exactly one context (`workctx mcp serve`) exposing the frozen version 1 surface: 11 read tools and 6 approval-gated mutation tools (ADR 0012).
- Adapter installers for Codex, Claude Code, and Gemini CLI (`workctx agent detect|status|install|open`): bridge files, portable skills, and project-scoped MCP configuration, generated with a plan-first, approval-gated flow that never rewrites user-owned configuration.

### Legacy migration

- Deterministic conversion of an existing Markdown work repository into a new isolated context (`workctx migrate legacy`), preview-first, with inventory classification, safety findings, reference conversion, and full reports. A migration apply is recorded as one audited import transaction, and the source tree is never modified.

## Known limitations

- **Projections are rebuild-only.** There are no incremental updates: a successful `transaction apply` refreshes the SQLite projection by rebuilding it, direct file edits require `workctx index rebuild`, and generated views always require `workctx view rebuild`. Incremental projection updates are planned after the alpha.
- **MCP transport is stdio only.** One server process per context, launched by the MCP client. There is no HTTP or socket transport and no MCP prompts or subscriptions in the version 1 surface.
- **No external writes, connectors, or UI.** By design in Phase 1: drafts stay local, nothing is sent, and there are no Jira/GitHub/email integrations. See [`ROADMAP.md`](../../ROADMAP.md).
- **Migration constraints.** `workctx migrate legacy` requires UTF-8 Markdown with parseable YAML frontmatter for canonical documents; type inference is limited to supported directory names, explicit type fields, and recognized ID prefixes; duplicate IDs resolve to the first path in deterministic order with recorded precision loss; task hierarchies deeper than parent/subtask are flattened and reported; generated and obsolete files are not migrated; and heuristic safety findings can require operator review — flagged source bytes are never copied even with `--allow-findings`. See the [migration reference](../reference/migration.md).
- **Local filesystems only.** Locking and atomicity guarantees are stated for NTFS, APFS, and ext4. Network filesystems (SMB, NFS) receive no additional guarantees.
- **Alpha hardening.** Secret and prompt-injection detection is heuristic, and the test gate enforces a line-coverage floor of 82 percent — meaningful, not exhaustive. Review evidence and proposals before approving them.

## Upgrade and stability policy

- **Workspace schema.** Contexts declare a single integer `schema_version` (currently `1`). Schema changes ship as forward-only migrations registered in the core package; applying will always back up canonical files first, and downgrade is restore-from-backup, never reverse migration (ADR 0007). Pre-1.0, the workspace schema may advance with minor releases; every released schema version will have a migration to the next.
- **Projections.** SQLite databases and generated views are never migrated in place. A version mismatch triggers a full rebuild from canonical files, which is always a supported path.
- **MCP surface.** The version 1 tool surface is a public contract: within the 0.x line, changes are backward compatible or arrive as new tool names. Removing a tool is a breaking change and will not happen silently (ADR 0012).
- **CLI.** Exit bands and the JSON envelope documented in the [CLI envelope reference](../reference/cli-envelope.md) are the stable programmatic surface. Human-readable output may change between alphas; scripts should use `--json`.
- **General.** Backward-incompatible changes require migration support and a published architecture decision; raw evidence already in a context is retained and never silently rewritten.
