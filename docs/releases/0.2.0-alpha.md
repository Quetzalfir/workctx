# workctx 0.2.0-alpha

Release date: 2026-08-06

The second alpha completes the Phase 2 scope (operational intelligence over
the durable core) and the Phase 3 scope (controlled bridges to external
systems). Everything in [0.1.0-alpha](0.1.0-alpha.md) still holds; this
release adds on top without changing the workspace schema (`schema_version`
stays `1` — existing contexts need no migration).

## Features

### More views, faster projections

- Six new generated views join the original five, for eleven total:
  resource directory, status report, people directory, glossary, agenda,
  and suggestions (`workctx view rebuild`).
- Projection rebuild time cut roughly 4x on reference contexts by batching
  fsync barriers (133 to 9 per rebuild) without weakening any durability
  claim; batch `workctx inbox add` now takes one lock and one projection
  refresh for the whole batch.

### Secret references (ADR 0013)

- Contexts reference secrets by name only; values are never stored in a
  workspace, source control, logs, prompts, or reports.
- Resolution is environment-first (`WORKCTX_SECRET_<NAME>`), then the
  operating-system keyring under the `workctx` service.
- New `workctx secret` group: `set`, `check`, `list`, `unset`, and `import`.
  Listing shows names and resolution state, never values, and secret values
  are handled through an opaque type whose only accessor is an explicit
  `reveal()` — they cannot leak through repr, logging, or serialization.

### Personalization layers

- A user-level `instructions.md` (in the workctx user config directory) and
  a context-root `instructions.md` are merged into all three agent bridge
  files at `workctx agent install`, so operator guidance survives adapter
  updates instead of living in hand-edited generated files.
- Per-context skill overrides under `06_overrides/skills/<name>/SKILL.md`
  take precedence over packaged skills, with three-way drift markers when
  the packaged original moves ahead of an override.

### Assisted improvement loop (opt-in)

- Optional usage telemetry, off by default and local-only, records which
  commands and skills a context actually uses (`telemetry` block in
  `context.yaml`).
- `workctx usage status|evaluate|suggest` and
  `workctx suggestion list|show|adopt|reject` turn that record into
  reviewable improvement suggestions; nothing is ever adopted
  automatically, and suggestion records share the audit ledger timeline.

### Connectors (read-only external evidence)

- A generic, on-demand connector runtime snapshots external systems into
  ordinary inbox evidence: snapshots arrive as `external_snapshot` artifacts
  with `source_origin` set to `connector:<name>`, passing through the same
  quarantine and safety scanning as any other evidence.
- `workctx connector list|sync|status` with optional per-snapshot schedules
  and due-state reporting; secrets are referenced by name (ADR 0013) and
  connector responses are treated as untrusted data end to end.
- A browser-capture skill covers systems whose APIs are blocked or
  unavailable: the operator's agent captures what the operator can already
  see on screen and registers it as evidence (see the
  [browser capture guide](../guides/browser-capture.md)).

### Outbox send (ADR 0014) — the first external write

- `workctx outbox send` publishes an approved draft through a configured
  channel, starting with GitHub (issue and pull-request comments).
- Preview-first and per-operation approval (`--yes`), a content fingerprint
  to prevent duplicate sends, and honest failure semantics: a remote
  success with a local recording failure is surfaced for reconciliation,
  never papered over. External writes remain off unless a channel is
  explicitly configured.

### Context inventory

- A machine-local context registry: `workctx context register|list|unregister`
  keep an inventory of contexts across the filesystem, and `context list`
  reports per-context entity counts at a glance.

### Agent adapter recovery

- `workctx agent repair` and `workctx agent uninstall` complete the adapter
  lifecycle: plan-first restoration of deleted or drifted generated files,
  and removal of manifest-owned files only — canonical context files are
  never touched.
- `workctx agent install --agent all` targets the clients actually detected
  on the machine and reports the skipped ones instead of failing outright.
- Template-shipped bridge files are recognized by content hash, so fresh
  contexts regenerate their bridges (and receive personalization) instead
  of treating the packaged template as an operator edit.
- Validation diagnostics now carry a machine-readable `repair_action` in
  the JSON envelope alongside the human repair guidance.

## Known limitations

- **One send channel.** GitHub is the only outbox channel; additional
  channels (Jira, Teams, email) arrive one at a time, each behind the same
  approval gate.
- **Connectors are generic and on-demand.** There are no per-service
  integrations or daemons; schedules mark snapshots as due, and syncs run
  when invoked. Service-specific setup (tokens, scopes) is the operator's,
  guided by the integration entities in each context.
- **Telemetry is local and heuristic.** Usage records never leave the
  context, and suggestion quality depends on real usage volume.
- **No UI.** Deferred by decision D-046; the CLI and MCP surfaces remain
  the only interfaces.
- The 0.1.0-alpha limitations on projections, MCP transport, migration,
  local filesystems, and alpha hardening still apply.

## Upgrade and stability policy

- The workspace schema is unchanged (`schema_version: 1`); 0.1.0-alpha
  contexts work as-is. New optional blocks (`telemetry`, connector and
  outbox configuration) validate under the same schema and default to off.
- The MCP version 1 tool surface is unchanged. CLI exit bands and the JSON
  envelope remain the stable programmatic surface; the envelope gained the
  optional `repair_action` diagnostic field (additive).
- The policies stated in [0.1.0-alpha](0.1.0-alpha.md#upgrade-and-stability-policy)
  continue to apply.

## Install

See the [README](../../README.md#install) for source installation with
`uv tool install` or `pipx`, and the [quick start](../guides/quickstart.md)
for the full first-run walkthrough. Upgrading in place:
`uv tool upgrade workctx` (or reinstall from the tag).
